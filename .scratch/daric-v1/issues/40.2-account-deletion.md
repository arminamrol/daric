# 40.2: Account deletion and ownership transfer

**What to build:** A user permanently deletes their account and data after re-authenticating; if their Workspace has other Members they must transfer ownership first.

**Blocked by:** 40.1

**Status:** done

- [x] Ownership transfer endpoint and UI
- [x] Deletion requires re-auth; sole-owner Workspaces are hard-deleted
- [x] Audit rows kept with the actor anonymised
- [x] HTTP tests prove no remaining personal data
- [x] If the User has active Plus time, deletion warns that it is forfeited; payments rows kept anonymised for accounting

## Comments

Notes for later tickets:

- Transfer: `POST /v1/workspaces/:wsId/members/:memberId/transfer-ownership` (Owner only, 204). The Member becomes Owner and the former Owner an Admin, audited as `workspace.transfer_ownership` with `fromUserId`/`toUserId`. The Owner's membership row is locked (`FOR UPDATE`) and the role re-checked inside the transaction so two transfers at once cannot make two Owners. No password asked; the web asks once more in place (`ConfirmButton`). The former Owner gets no `WORKSPACE_SHARING` Consent row (`daric_app` cannot insert Consents); they can still leave through the members route.
- Deletion: `GET /v1/me/deletion` previews `{ sharedWorkspaces, deletedWorkspaces, plusForfeitedUntil }`; `POST /v1/me/deletion { password }` deletes (204, web cookies cleared). 403 `reason: WRONG_PASSWORD`, 409 `reason: OWNS_SHARED_WORKSPACE` with `sharedWorkspaces`. `@ChecksPassword()` (`modules/auth/checks-password.ts`) puts a route under the auth rate limit; use it for any other route that checks a password.
- `AccountDeletionService` (`modules/me`) runs on the owner connection in one transaction: locks the User and their owned Workspaces, refuses if any has other Members, records `account.delete` (no actor, `{ role }`) in every Workspace they only joined, deletes owned Workspaces (cascade), anonymises audit rows (actor, IP and user agent where they acted; any metadata key whose value is their id), takes their email off Invitations (revoking any still pending, since an email-less Invitation is a link anyone may accept), then deletes the User (cascades to identities, refresh tokens, email tokens, memberships, Consents, Subscription; `created_by` and invitation `*_by_user_id` go null).
- `plusForfeitedUntil` is set only for bought Plus time (billing enabled, Plus, not on the Trial). There is no `payments` table yet: 42 must give it `user_id ... ON DELETE SET NULL`, keep no email or card data on it, and add it to the "no personal data" test in `account-deletion.http.test.ts` (which scans every table's rows as text for the User's id and email).
- New tables holding personal data must be covered by that scan: either cascade from `users`/`workspaces`, `SET NULL`, or be scrubbed in `AccountDeletionService`.
- Web: `/settings/delete-account` (link at the bottom of Settings). A shared owned Workspace shows "Choose a new owner", which switches to it and opens Members, where the Owner sees "Make owner" per Member. `useForgetSession()` (`auth/logout.ts`) wipes the device after a logout or a deletion. Mobile has no deletion or transfer screen yet; `deleteAccount` in the api-client already forgets the mobile tokens on success.
